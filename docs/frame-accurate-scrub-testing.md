# Frame-Accurate Scrub Testing

This runbook is the permanent entry point for validating playback, jogging, and
scrub-preview correctness. It exists so future agents do not have to rediscover
the numbered-frame fixture, WebSocket control flow, capture paths, and iOS
device quirks from scratch.

The target behavior is strict: when the transport is paused and the operator
steps or scrubs to frame N, PGM must submit frame N promptly and predictably.
The visible preview should follow quickly, but preview is not the authority for
command success. Lower-framerate inputs may legitimately hold the same visual
image for multiple output frames, so the tests use embedded marker numbers
rather than pixel-difference assumptions.

Operator seeks and jog steps use stricter coverage than passive preview. A
preview may display a lower-cadence held frame, but an operator transaction must
not report success from a stale prior source frame. Valid operator coverage is
an exact frame, the immediately preceding source frame within one output tick,
or a tiny timestamp-rounding future frame.

## Test Ladder

Run the fastest useful layer first, then climb until the actual target device is
covered:

1. Unit tests around `PlaybackWorker` cache coverage and seek commit behavior.
2. macOS app visual E2E with WebSocket control and OS-level screenshots.
3. iOS/iPadOS local SRT marker oracle with WebSocket control and device-file
   preview captures.
4. Optional physical-device OS screenshots when `pymobiledevice3` or
   `idevicescreenshot` can see the device.

The app's `capture.current` JPEGs prove what the preview provider is producing.
OS screenshots prove what is actually visible on screen. Prefer OS screenshots
when available; use device-file preview captures on iOS when CoreDevice works
but usbmux screenshot tools cannot see the device.

PGM output is the broadcast authority. Preview and screen captures are still
important, but a professional replay command is considered proven only when the
PGM path submits the requested frame. For device runs, enable a unique PGM NDI
sender and let `ndi_recv_probe --stream-markers` decode the same marker that the
preview JPEG later confirms. If both the WebSocket ACK's `pgmTransaction` and
the external PGM NDI marker match, the app has delivered the requested frame to
the programme output path.

Wi-Fi NDI note: when the iPad and the receiver Mac are both on Wi-Fi, the NDI
receiver may drop packets. The oracle therefore drains stale receiver frames
before each command and waits for the next received copy of the expected marker.
Do not use raw NDI packet continuity over Wi-Fi as the app correctness gate.
Use exact marker identity per operator command. If the command produced the
wrong marker, a stale marker, or no marker before timeout, that is an app failure.
If a long soak needs packet-continuity guarantees, use wired Ethernet or a
single-machine/macOS loopback run.

Preview freshness note: `FrameProvider` restamps frames onto a monotonic
delivery-time presentation clock and leaves `QVideoFrame::endTime()` invalid
(`-1`) so paused jog/scrub frames remain displayable until replaced. Synthetic
serial timestamps or tiny explicit end times can make Qt `VideoOutput` treat
paused frames as expired or stale after a few jog steps. If visible preview
freezes while `capture.current` or provider JPEGs are correct, inspect the
`QVideoSink` -> Qt Quick presentation boundary. If provider JPEGs are stale too,
inspect Qt preview readback and `FrameProvider` serial flushing first.

Qt presentation note: a successful `QVideoSink` flush proves that Qt received
the frame, not that the Qt Quick scene graph has rendered and presented it to
the display. VSync, the render loop, and QRhi/swapchain buffering can therefore
make OS screenshots lag provider captures. Keep that separate from PGM: PGM NDI
is an output endpoint outside Qt Quick, and its command-to-marker latency is the
authority for the broadcast output path.

GPU readback note: paused operator commands use the synchronous
`submitAndFlush` path. GPU-backed frames on that path must wait the producer
fence, read back the requested frame, and call the inner sink's
`submitAndFlush` exactly once. They must not enqueue the frame and race the
async readback worker; that can make preview freshness depend on worker timing
instead of the operator transaction.

## Marker Fixture

The marker fixture is generated by `ndi_marker_mkv_source` and decoded by
`marker_yuv_probe`. Each video frame carries a machine-readable frame number in
the luma plane; the fixture also includes audio. This makes the test independent
of visual motion in the scene. PGM NDI latency is measured with
`ndi_recv_probe --stream-markers` when the NDI runtime is installed.

Build the desktop test tools:

```sh
cmake --build build/c --target ndi_marker_mkv_source marker_yuv_probe ndi_recv_probe -j 8
```

For playback-worker changes, run the focused unit target before device work:

```sh
cmake --build build/c --target tst_playbackworker -j 8
./build/c/tests/unit/tst_playbackworker
```

## macOS Visual Oracle

The macOS app E2E is the fastest full app loop. It launches the app with the GPU
path enabled, configures a local SRT marker source over the WebSocket API,
records long enough to seek backward, then runs this operator sequence:

- start stream and record
- wait for at least 30 seconds of recording
- pause
- seek to 30 seconds
- step back 60 frames, one frame at a time, with 500 ms between steps
- step forward 15 frames
- step back another 30 frames
- perform three cold seeks whose targets are each more than five seconds away
  from the current playhead

The cold-seek requirement is deliberate: adjacent frame steps can hit warm
buffers, but professional replay seeking must also prove the full MKV -> seek ->
playhead -> output path when the requested frame is outside any local decode or
readback buffer. The current macOS gate seeks `825 -> 120`, `120 -> 840`, and
`840 -> 60` at 30 fps, so each latency sample jumps at least 23.5 seconds.

It validates visible correctness with OS-level screenshots. macOS
`screencapture` is intentionally not the low-latency oracle because capture,
focus, file write, and marker-probe overhead can dominate the measured time.
When `ndi_recv_probe` is available, the wrapper enables a unique PGM NDI sender
and runs in strict latency mode: every jog step plus every cold seek must reach
that external output below the configured latency threshold, and the run must
report all 108 latency samples. The default threshold is 25 ms; the current
professional target is 15 ms and should be run explicitly with
`OLR_APP_E2E_LATENCY_THRESHOLD_MS=15`. The app-side ACK is also checked for PGM
transaction metadata, so a command cannot pass by acknowledging request
acceptance before PGM submit.

Run through CTest:

```sh
OLR_APP_E2E_LATENCY_THRESHOLD_MS=15 \
  ctest --test-dir build/c -R e2e_macos_app_visual --output-on-failure
```

Or run the shell wrapper directly if you need to choose ports/workdirs:

```sh
tests/e2e/run_macos_app_visual_e2e.sh \
  build/c/OpenLiveReplay.app/Contents/MacOS/OpenLiveReplay \
  build/c/tests/e2e/ndi_marker_mkv_source \
  build/c/tests/e2e/marker_yuv_probe \
  build/c/tests/e2e/ndi_recv_probe
```

Failure artifacts include the app log, captured preview JPEGs, OS screenshots,
NDI marker timing, and marker decode output in the wrapper's workdir. A
successful run ends with a line like:

```text
APP_E2E_PASS primeFrame=900 backward60=60 forward15=15 backward30=30 coldSeek=3 ndiLatencySamples=108 expectedNdiLatencySamples=108 max_ndi_latency_ms=23.65
```

When debugging a late-run stale-frame failure, compare `APP_NDI_LATENCY` with
`OLR_LATENCY control.command` and `OLR_LATENCY ndi.submit` in the app log. For a
correct operator seek, the transaction target, sampled playhead, and source PTS
should all identify the requested marker frame, apart from known timestamp
rounding offsets.

## iOS Local SRT Oracle

Use this when validating the iPad/iPhone build. The oracle starts a local SRT
marker stream on the Mac, pushes a one-source marker config into the app's data
container with `devicectl`, optionally relaunches the app with GPU/WebSocket test
environment, drives the app over WebSocket, captures PGM preview JPEGs on the
device, pulls them back with `devicectl`, and decodes the marker numbers.
When `--ndi-recv-probe` is supplied, it also configures PGM NDI in the app and
validates every command against the external PGM output.

Prerequisites:

- app installed on the iOS/iPadOS device
- device unlocked
- Mac and device on the same LAN when using Wi-Fi WebSocket/SRT
- Xcode `xcrun devicectl`
- `ffmpeg` and `srt-live-transmit`
- built `ndi_marker_mkv_source` and `marker_yuv_probe`

Find the CoreDevice identifier:

```sh
xcrun devicectl list devices
```

Find the Mac LAN address reachable by the iPad:

```sh
ipconfig getifaddr en0
```

Find the app WebSocket host after launch. If the device is on
`192.168.68.0/24`, for example:

```sh
for ip in 192.168.68.{2..254}; do
  (nc -G 1 -z "$ip" 8115 && echo "$ip") &
done
wait
```

Run the oracle:

```sh
python3 tests/e2e/ios_marker_srt_oracle.py \
  --device <coredevice-id> \
  --app-host <ipad-wifi-ip> \
  --mac-host <mac-lan-ip> \
  --marker-source build/c/tests/e2e/ndi_marker_mkv_source \
  --marker-probe build/c/tests/e2e/marker_yuv_probe \
  --workdir /tmp/olr-ios-marker-oracle \
  --keep-workdir \
  --launch-app
```

Preferred PGM-output run, including the 105-step jog sequence plus three cold
seeks that each jump more than five seconds from the previous playhead:

```sh
python3 tests/e2e/ios_marker_srt_oracle.py \
  --device <coredevice-id> \
  --app-host <ipad-wifi-ip> \
  --mac-host <mac-lan-ip> \
  --marker-source build/c/tests/e2e/ndi_marker_mkv_source \
  --marker-probe build/c/tests/e2e/marker_yuv_probe \
  --ndi-recv-probe build/c/tests/e2e/ndi_recv_probe \
  --ndi-sender-name "OLR iPad Marker PGM Full" \
  --workdir /tmp/olr-ios-ndi-oracle-full \
  --keep-workdir \
  --launch-app \
  --marker-seconds 180 \
  --warmup-seconds 32 \
  --target-ms 30000 \
  --steps=-1x60,+1x15,-1x30 \
  --cold-seek-frames 120,840,60 \
  --ndi-marker-timeout 3.0
```

Defaults:

- marker source: 30 fps, 180 seconds
- warmup: 30 seconds of recording
- target: 30000 ms
- step sequence: `-1x60,+1x15,-1x30`
- per-step delay: 500 ms
- app launch env: `OLR_CONTROL_BIND=any`, `OLR_PB_TELEMETRY=1`,
  `OLR_GPU_PIPELINE=1`

The expected successful summary has `failCount` equal to zero:

```text
SUMMARY {"failCount": 0, "stepCount": 105, ...}
```

The PGM NDI form also reports `coldSeekCount`. A known-good iPad run from
2026-07-08 ended with:

```text
SUMMARY {"coldSeekCount": 3, "failCount": 0, "firstMarker": 1156, "lastMarker": 316, "srtUrl": "srt://192.168.68.51:32900?transtype=live", "stepCount": 105}
```

Every step and cold seek in that run emitted:

- `PGM_ACK`: the WebSocket command waited for the PGM transaction to complete.
- `NDI_MATCH`: the external PGM NDI receiver observed the exact expected marker.
- `CAPTURE`/`STEP`/`COLD_SEEK`: the pulled device PGM JPEG decoded to the exact
  expected marker.

The workdir contains:

- `results.json`: expected marker, observed marker, position, and capture path
  for every step
- `ndi-recv-probe.log`: raw PGM NDI marker observations when NDI validation is
  enabled
- `captures/`: pulled PGM preview JPEGs
- `ffmpeg-stream.log` and `srt-live-transmit.log`
- `config.original.json` and `config.local-marker.json`

By default the oracle restores `Documents/settings/config.json` on exit. Use
`--no-restore-config` only for deliberate manual follow-up.

Cold-seek target rules:

- Each cold target must be more than `--cold-seek-min-distance-ms` away from the
  immediately previous playhead, not merely from the original target.
- Avoid frame 0/head-of-recording for the normal robustness gate. Exact head
  seeking is a separate first-frame acquisition test; the cold-seek gate should
  exercise stable content inside the recorded window.
- At 30 fps, `--cold-seek-frames 120,840,60` from the default sequence jumps
  approximately 23.5 s, 24 s, and 26 s.

## Restore Rally SRT Sources

The iOS oracle restores the prior device config unless `--no-restore-config` was
used. If manual testing leaves the app on a local marker source, restore the four
production rally sources over WebSocket:

```sh
PYTHONPATH=tests/e2e python3 - <<'PY'
from macos_app_driver import WsClient

host = "<ipad-wifi-ip>"
ws = WsClient(host, 8115, timeout=5)
ws.wait_for(lambda: bool(ws.state), 5, "state snapshot")

urls = [
    "srt://maps.rally.promo:8890?streamid=read:stream1",
    "srt://maps.rally.promo:8890?streamid=read:stream2",
    "srt://maps.rally.promo:8890?streamid=read:stream3",
    "srt://maps.rally.promo:8890?streamid=read:stream4",
]

while len(ws.state.get("sources", [])) < len(urls):
    previous_count = len(ws.state.get("sources", []))
    ws.command("sources.add")
    ws.wait_for(
        lambda: len(ws.state.get("sources", [])) >= previous_count + 1,
        5,
        "source add",
    )

for index in range(len(ws.state.get("sources", [])) - 1, len(urls) - 1, -1):
    ws.command("sources.remove", {"index": index})

for index, url in enumerate(urls):
    ws.command("sources.updateUrl", {"index": index, "url": url})
    ws.command("sources.updateName", {"index": index, "name": f"CAM{index + 1}"})
    ws.command("sources.updateId", {"index": index, "id": f"maps-stream-{index + 1}"})

ws.command(
    "outputs.ndi.setSenderName",
    {"busKind": "pgm", "feedIndex": -1, "senderName": "OLR iPad PGM Maps"},
)
ws.command("outputs.ndi.setEnabled", {"busKind": "pgm", "feedIndex": -1, "enabled": True})
ws.command("settings.save")
ws.close()
PY
```

```sh
  --device <coredevice-id> \

  --environment-variables '{"OLR_GPU_PIPELINE":"1","OLR_PB_TELEMETRY":"1","OLR_CONTROL_BIND":"any"}' \
```

```sh
xcrun devicectl device info files \
  --device <coredevice-id> \
  --domain-type appDataContainer \
  --domain-identifier com.timokorkalainen.OpenLiveReplay \
  --subdirectory Documents \
  --columns '*' \
  -r

  --device <coredevice-id> \
  --domain-type appDataContainer \
  --domain-identifier com.timokorkalainen.OpenLiveReplay \
  --source Documents/videos/<file> \
  --destination /tmp/<file>
```

## Optional Physical Screen Capture

When usbmux tools can see the device, take an OS-level screenshot to verify the
literal visible screen:


capture, not a physical screen capture.

## Troubleshooting

- WebSocket not reachable: relaunch with `OLR_CONTROL_BIND=any`, verify the app
  is foregrounded/unlocked, then scan port `8115` again.
- SRT source not connected: verify `--mac-host` is the Mac LAN address reachable
  from the iPad, and that no old producer is occupying `--srt-port`.
- `srt-live-transmit` logs packet loss before the app connects: this is normal
  while the producer is waiting for a client.
- Preview captures collide or stale JPEGs are pulled: the iOS oracle changes the
  project name before each `capture.current`; do not replace that with a static
  project name.
- Black or blue frames at startup: keep the 30 second warmup and inspect the
  source `connected` state plus `results.json`. A valid test must prove marker
  numbers from input through app output, not only that recording duration
  advanced.
- Scrub latency regression: the macOS visual oracle has two jobs. PGM NDI
  marker timing is the command-to-output latency gate; OS screenshots prove the
  screen eventually shows the same requested marker and must not be treated as a
  sub-frame latency timer unless replaced by a faster OS-level screen watcher.
